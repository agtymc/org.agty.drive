# Техническое задание: AGTY/DRIVE

## 1. Цель
Разработать легкий web-сервис для хранения и обмена файлами, визуально и сценарно близкий к Яндекс.Диску и Google Drive, но в упрощенной форме. Продукт должен позволять пользователю загружать файлы через форму и drag-and-drop, создавать виртуальные директории, просматривать и скачивать файлы, архивировать директории, а также публиковать защищенные ссылки на файлы и каталоги.

## 2. Продуктовые ориентиры
За основу UX берутся паттерны Google Drive и Яндекс.Диска:
- левое дерево навигации и основная рабочая область;
- режимы отображения `list` и `grid`;
- контекстные действия над файлами и директориями;
- быстрый preview изображений и видео;
- публичные ссылки на файлы и папки;
- мультивыбор и групповые операции.

Из официальных материалов полезны следующие ориентиры: у Google Drive есть стандартные режимы `list/grid` и акцент на превью/шаринг, у Яндекс.Диска выражены drag-and-drop, доступ по ссылке, групповые действия и работа с публичными файлами/папками.

## 3. Границы MVP
### Входит в первую версию
- регистрация пользователей только администратором;
- логин/логаут;
- создание, переименование, удаление виртуальных директорий;
- загрузка файлов в выбранную директорию;
- drag-and-drop загрузка в браузере;
- просмотр содержимого директорий;
- переключение `list/grid`;
- просмотр изображений и видео без скачивания;
- скачивание файла;
- скачивание директории архивом;
- создание публичной ссылки на файл или директорию;
- срок действия ссылки;
- защита ссылки паролем;
- закрытый доступ по умолчанию;
- светлая и темная тема.

### Не входит в первую версию
- совместное редактирование;
- версионирование файлов;
- desktop sync;
- полнотекстовый поиск по содержимому файлов;
- chunk upload/resume upload;
- антивирусная проверка.

## 4. Архитектура
Текущий проект уже основан на Spring Boot 4, Thymeleaf, Spring Security и PostgreSQL. Это подходит для MVP.

Предлагаемая структура:
- `web/mvc` контроллеры для страниц кабинета, публичных ссылок и админки;
- `web/api` контроллеры для ajax-операций: загрузка, перемещение, удаление, preview, создание ссылок;
- `service` слой с бизнес-логикой;
- `repository` слой по образцу `org-agty-fsa-client`: явные SQL-запросы, отдельные entity/dto/converter/repository;
- `storage` слой для чтения/записи бинарных данных в файловом хранилище приложения;
- `security` для пользовательских ролей и публичных токенов.

Для работы с БД использовать тот же подход, что и в `/AGTY/WORK/work/AGTY/projects/FSA/app/org.agty.fsa/org-agty-fsa-client`: отдельный `DbConfig`, entity c аннотациями, ручные repository с SQL, DTO и converter-слой.

## 4.1 Соглашения по коду
Новый код должен повторять шаблон `org-agty-fsa-client` без упрощений и без замены на JPA.

- `Entity` — простые классы с аннотациями `AgtySQL`: `@Entity`, `@Table`, `@Id`, `@Column`.
- `DTO` — отдельные классы для UI и сервисов; валидация размещается именно в DTO.
- `Converter` — отдельный слой со статическими методами `rowToDto(...)`, `dtoToEntity(...)`.
- `Repository` — ручной SQL и работа только через `ConnectionPool.POOL.borrow()`.
- `Controller` — только orchestration уровня web; SQL в контроллерах и сервисах не размещается.
- Не использовать общие `Base*`, `Abstract*`, `Generic*` суперклассы для entity/dto/converter/repository/service только ради переиспользования. Отдельная предметная сущность должна иметь отдельный набор классов.

Структура контроллеров должна повторять проект-образец:
- `web/controllers/mvc/auth` — логин, выход, восстановление доступа;
- `web/controllers/mvc/cabinet` — пользовательский кабинет AGTY/DRIVE;
- `web/controllers/mvc/control` — админская часть;
- `web/controllers/api` — ajax/upload/share/preview endpoints.

## 4.2 Соглашения по AgtySQL
- `saveEntityWithCheck(...)` используется как основной способ сохранения сущностей.
- Если `@Id` в entity равен `null`, выполняется `INSERT`.
- Если `@Id` не `null`, выполняется `UPDATE`.
- Поэтому в edit-сценариях допустимо и ожидаемо делать `dto.setId(...)` до передачи в `service/repository`.

При чтении `SqlRow`:
- `getDstring(...)` использовать для пользовательских текстовых полей, где возможны кавычки, HTML entities и спецсимволы: `title`, `name`, `description`, `body`, `comment`, `original_filename`.
- `getString(...)` использовать для технических значений: `token`, `mime_type`, `extension`, `status`, `role`, `path_key`, `checksum`.
- `getBoolean(...)` может вернуть `null`, если поля нет в выборке или значение `NULL`, поэтому nullable-флаги нужно читать через `Boolean`, а не через примитивный `boolean`.

## 5. Модель данных
Физические директории на диске не создаются. Иерархия хранится в БД.

Основные таблицы:
- `agdrv_users` — пользователь, email/login, hash пароля, статус, роль;
- `agdrv_folders` — виртуальная директория: `id`, `owner_id`, `parent_id`, `name`, `path_key`, `created_at`, `deleted_at`;
- `agdrv_files` — метаданные файла: `id`, `folder_id`, `owner_id`, `name`, `extension`, `mime_type`, `size`, `checksum`, `created_at`;
- `agdrv_file_content` — legacy-таблица для миграции старых бинарных данных, не основной runtime storage;
- `agdrv_share_links` — публичные ссылки: `token`, `resource_type`, `resource_id`, `password_hash`, `expires_at`, `allow_download`, `allow_preview`, `created_by`;
- `agdrv_audit_log` — действия пользователя и администратора;
- `agdrv_user_invites` или `agdrv_registration_requests` — управление закрытой регистрацией.

Фактическое хранение бинарных данных в первой версии выполняется в файловой системе приложения. В БД хранятся только метаданные файла и служебные ссылки, а legacy BLOB/LO-данные допускаются только как источник миграции.

Все прикладные таблицы проекта должны использовать префикс `agdrv_`.
Все словари проекта должны использовать префикс `agdrv_dic_`.

Служебные таблицы Flyway не переименовываются и используют стандартное имя `flyway_schema_history`.

`agdrv_folders.parent_id` формирует дерево. Для быстрого построения хлебных крошек и проверки доступа желательно хранить дополнительный вычисляемый `path_key`.

## 6. Права доступа
- `ROLE_ADMIN` — создает пользователей, блокирует доступ, управляет регистрацией, просматривает аудит.
- `ROLE_USER` — работает только со своим пространством и своими публичными ссылками.
- Публичные ссылки не открывают доступ к аккаунту, а только к конкретному ресурсу по `token`.

По умолчанию:
- саморегистрация выключена;
- все файлы и директории приватны;
- preview и download через публичную ссылку доступны только если это явно разрешено.

## 7. Пользовательские сценарии
### Пользователь
1. Логинится.
2. Создает папку.
3. Перетаскивает файл в окно браузера или выбирает его через форму.
4. Видит файл в текущей директории.
5. Открывает preview, если формат поддерживается.
6. Скачивает файл или архивирует директорию.
7. Создает публичную ссылку, задает срок жизни и пароль.

### Администратор
1. Входит в админку.
2. Создает пользователя или выдает приглашение.
3. Блокирует или активирует учетную запись.
4. Управляет настройкой открытой/закрытой регистрации.

## 8. UI/UX
Интерфейс должен напоминать привычный cloud drive:
- слева: логотип, дерево папок, быстрые разделы;
- сверху: поиск по текущей директории, кнопки загрузки/создания/переключения вида;
- справа или в модальном окне: preview и свойства;
- основная область: список или сетка карточек файлов.

Режимы отображения:
- `List view` — таблица с колонками `Имя`, `Размер`, `Тип`, `Дата`;
- `Grid view` — плитки с превью, особенно полезно для изображений и видео.

Preview:
- изображения: встроенный просмотр;
- видео: HTML5 video player;
- остальные типы: иконка + метаданные + кнопка скачивания.

## 9. Визуальный стиль
В качестве визуальной базы использовать стиль проекта `/AGTY/WORK/work/AGTY/projects/org.agty.mtx`. Это касается только стилей, а не архитектуры проекта или структуры кода.

Ключевые визуальные принципы:
- тема по умолчанию — `dark`;
- палитра на основе темного фона, двух уровней поверхностей и приглушенных границ;
- акцентный цвет — спокойный зеленовато-бирюзовый;
- интерфейс должен выглядеть как плотное desktop-like web-приложение, а не маркетинговый лендинг;
- брендовый блок и отдельные заголовочные элементы допустимо строить на моноширинной типографике в духе `AGTY/MTX`;
- карточки, сайдбар, список файлов, модальные окна и панели preview должны иметь четкие границы и спокойный контраст без лишней декоративности.

Тема `dark`:
- фон в диапазоне `#343541` / `#202123` / `#2a2b32` или близких значений;
- текст светлый, вторичный текст приглушенный;
- границы темные, но читаемые;
- кнопки, поля и панели должны визуально повторять ритм `AGTY/MTX`;
- это основной режим, который нужно прорабатывать первым.

Тема `light`:
- остается в проекте как вторичная возможность;
- строится на той же системе токенов и отступов;
- может быть реализована позже и не является приоритетом на раннем этапе;
- стиль должен быть производным от темной темы, а не отдельным визуальным языком.

## 10. Нефункциональные требования
- Java 21.
- PostgreSQL как основная БД.
- Ограничение размера загружаемых файлов настраивается.
- Потоковая выдача файлов без полной загрузки в память приложения.
- Проверка MIME-типа и безопасных имен файлов.
- CSRF, защита сессии, bcrypt/argon2 для паролей.
- Логи действий и ошибок.

## 11. Этапы реализации
### Этап 1. Основа
- схема БД;
- модели `users/folders/files/share_links`;
- security, логин, роли;
- базовый кабинет.

### Этап 2. Файловый менеджер
- создание директорий;
- list/grid;
- загрузка файлов;
- просмотр содержимого;
- скачивание файла.

### Этап 3. Preview и публикация
- preview изображений и видео;
- публичные ссылки;
- пароль и срок действия;
- публичный просмотр папки.

### Этап 4. Архивация и админка
- скачивание директории архивом;
- управление регистрацией;
- аудит и управление пользователями.

## 12. С чего начинать
Начинать нужно с проектирования схемы БД и модели доступа, потому что вся логика продукта держится на виртуальном дереве папок, правах и публичных ссылках. Сразу после этого я бы сделал каркас security и минимальный кабинет: логин, список папок пользователя, создание папки и загрузку одного файла. Это даст рабочее ядро, вокруг которого уже можно безопасно наращивать preview, архивирование, list/grid и публичный шаринг.
